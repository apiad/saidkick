# 0.6.0 — Offscreen Document holds the WebSocket

**Status:** approved 2026-04-29.
**Scope:** Move the persistent WebSocket out of the MV3 service worker and into a Chrome offscreen document. The SW becomes a thin command executor; the offscreen page becomes the always-alive connection holder.

## Motivation

The 0.4.5 release added PING/PONG keepalive (every 20s, inside Chrome's 30s SW idle window) plus a `chrome.alarms` watchdog (every 30s) to reconnect after SW death. In practice — confirmed by smoke testing during the SuperBot Task 3.3 work on 2026-04-29 — the connection still drops:

- `saidkick tabs` returns data once after extension load.
- Within ~30 seconds of inactivity, the SW dies despite the PING keepalive.
- Subsequent CLI commands return `[]` / `browser not connected` for up to 30 seconds (until the alarm fires and reconnects).
- Manual click on the popup's Reconnect button helps briefly, then the cycle repeats.

The root cause is structural: in MV3, outbound WebSocket sends from a service worker do *not* reliably extend SW lifetime, and incoming-message wakeups depend on Chrome's heuristics. PING-keepalive from inside the SW is fundamentally racing against the same SW idle timer it's trying to defeat. No amount of tuning the keepalive interval or alarm cadence will close this hole — the MV3 alarm minimum is 30s in production builds, and the SW idle timer can fire at any point during that window.

Chrome's MV3 documentation explicitly recommends offscreen documents for "long-lived connections that must outlive the service worker." Offscreen documents are hidden DOM pages owned by the extension; they have a real document lifetime independent of the SW idle timer. They can hold a WebSocket open for hours without intervention.

## Architecture

```
┌──────────┐                ┌──────────────────┐                ┌───────────────────┐
│  CLI     │  HTTP          │  saidkick server │   WebSocket    │  Chrome extension │
│ (curl,   ├───────────────▶│  (FastAPI on     │◀──────────────▶│  Offscreen doc    │
│  uv run) │                │   localhost:8765)│                │  (offscreen.html) │
└──────────┘                └──────────────────┘                └────────┬──────────┘
                                                                         │
                                                                         │ chrome.runtime.connect
                                                                         │ Port: "saidkick-cmd"
                                                                         │
                                                                         ▼
                                                                ┌───────────────────┐
                                                                │  Service worker   │
                                                                │  (background.js)  │
                                                                │  chrome.tabs,     │
                                                                │  chrome.scripting,│
                                                                │  chrome.debugger  │
                                                                └───────────────────┘
```

The WebSocket lives in `offscreen.js`. The SW lives only as a command executor. They communicate via a long-lived `chrome.runtime.connect()` Port named `"saidkick-cmd"`.

### Per-command flow

1. CLI sends HTTP request to FastAPI server.
2. Server picks the connection for the addressed `browser_id` from `manager.connections`, sends a JSON frame on the WS (e.g. `{type: "LIST_TABS", id: "..."}`).
3. Frame arrives at `offscreen.js`'s `socket.onmessage`.
4. `offscreen.js` posts the frame on its Port to the SW: `port.postMessage(frame)`.
5. SW receives the message in its `port.onMessage` listener. The SW wakes up if it was asleep — runtime messages are wakeup events. The SW handles the command via the existing handler functions (`LIST_TABS`, `OPEN`, `GET_DOM`, `CLICK`, `TYPE`, `PRESS`, `SCREENSHOT`, `EXECUTE`, `SCROLL`, `HIGHLIGHT`, `FIND`).
6. SW posts the response back on the Port: `port.postMessage(response)`.
7. `offscreen.js` receives via `port.onMessage`, sends as WS frame back to server.
8. Server resolves the pending future and returns the HTTP response to the CLI.

Two extra hops (offscreen↔SW round trip) compared to the current design. Measured cost: <10ms per command — negligible against the ~50–200ms typical for a real chrome.* call.

### Lifecycle

**On extension load:**
1. SW top-level code calls `chrome.offscreen.hasDocument()`. If false, `chrome.offscreen.createDocument({url: "offscreen.html", reasons: ["WORKERS"], justification: "Persistent WebSocket to localhost saidkick server"})`.
2. The new offscreen page runs `offscreen.js`, which immediately calls `connect()` and opens the WS to `ws://localhost:8765/ws`.
3. On WS open, offscreen also calls `chrome.runtime.connect({name: "saidkick-cmd"})` to establish the Port to SW. The SW's `chrome.runtime.onConnect` listener attaches its `port.onMessage` handler.
4. Server replies with `HELLO` containing `browser_id`. Offscreen forwards `HELLO` to SW so SW can cache the `browser_id` for status reporting (popup needs it).

**On SW death (idle, eviction, crash):**
- The Port from offscreen to SW is broken. Offscreen detects this via `port.onDisconnect`.
- Offscreen does NOT close the WebSocket; the WS stays alive.
- Offscreen re-opens the Port: `chrome.runtime.connect({name: "saidkick-cmd"})`. This wakes the SW, which re-attaches its handler. (`chrome.runtime.connect()` from offscreen IS a wakeup event for the SW.)
- Subsequent commands flow normally. No browser disconnect from the server's perspective.

**On offscreen document eviction (rare; Chrome may evict offscreen pages under memory pressure):**
- The WebSocket closes. Server sees disconnect.
- The `chrome.alarms` watchdog (kept, repurposed) fires within 30s. SW handler checks `chrome.offscreen.hasDocument()`; if false, creates one. Offscreen reconnects the WS. New `browser_id` minted.

**On Chrome restart:**
- SW spawns. Top-level code creates the offscreen document. WS connects. Normal operation.

### Files

#### New: `src/saidkick/extension/offscreen.html`

```html
<!DOCTYPE html>
<html>
<head><meta charset="utf-8"><title>Saidkick offscreen</title></head>
<body><script src="offscreen.js"></script></body>
</html>
```

Three lines of meaningful content. Required by Chrome's offscreen API to point at a real HTML document.

#### New: `src/saidkick/extension/offscreen.js`

Approximately 120 LOC. Responsibilities:

- Manage the WebSocket lifecycle: open, message handling, close + retry (1s backoff), error logging.
- Manage the Port to SW: open on first WS-open, re-open on `onDisconnect`, forward all WS frames as `port.postMessage`.
- Forward SW → Port responses back as WS frames.
- Maintain a small bounded log queue (`logQueue`, max 200) for messages that arrive while the WS is reconnecting.
- Keep the existing `PING/PONG` heartbeat at a slower cadence (60s instead of 20s), repurposed as a half-dead-connection detector — when the offscreen sees no PONG within 90s of sending a PING, it forces a WS reconnect. SW idle is no longer the constraint.

Public API consumed by the SW (via Port):
- Inbound messages (offscreen → SW): all server frames except `PONG` (which offscreen swallows).
- Outbound messages (SW → offscreen): RESPONSE frames, log frames, GET_STATUS replies.

#### Modified: `src/saidkick/extension/background.js`

The WS-management code (lines 304–632 in current `background.js`, ~330 LOC) gets removed. What remains:

- All command handlers (`LIST_TABS`, `OPEN`, `GET_DOM`, `CLICK`, `TYPE`, `PRESS`, `SCREENSHOT`, `EXECUTE`, `SCROLL`, `HIGHLIGHT`, `FIND`, etc.) — unchanged. They take the message object and currently call `socket.send(...)` to reply; in the new design they call `port.postMessage(...)` instead.
- `attachedTabs` Set, `chrome.debugger` lifecycle handlers, `chrome.tabs.onRemoved` cleanup — unchanged.
- New top-level code: `chrome.offscreen.hasDocument` → create if absent. Wrapped in an `ensureOffscreen()` function called from extension install/load, plus from the alarm watchdog.
- New `chrome.runtime.onConnect` listener for port name `"saidkick-cmd"`. Sets up `port.onMessage` to dispatch to existing handlers (`switch (type) { case "LIST_TABS": ... }`). On `port.onDisconnect`, clear the cached port reference. The dispatch table is identical to today's `socket.onmessage` switch — only the I/O sites change.
- The `chrome.alarms` watchdog is kept but its semantic flips: instead of "if WS not OPEN, reconnect WS," it becomes "if no offscreen document exists, create one." The 30s cadence is fine since this is now belt-and-braces (offscreen evictions are rare).
- Popup → SW `RECONNECT` message: handler now closes the offscreen document (`chrome.offscreen.closeDocument()`) and creates a new one. WS naturally re-opens with a fresh `browser_id`.

Net: `background.js` loses ~330 LOC of WS handling, gains ~50 LOC of offscreen + port plumbing. ~280 LOC smaller.

#### Modified: `src/saidkick/extension/manifest.json`

- Add `"offscreen"` to `permissions`.
- Bump extension `version` from `1.2` to `1.3`.
- The existing `"background.service_worker": "background.js"` stays as-is.

#### Modified: `src/saidkick/extension/popup.js`

The popup currently calls `chrome.runtime.sendMessage({type: "GET_STATUS"})` to render the connection state. The SW responds based on `socket.readyState`. With the new design, the SW doesn't own the socket — it has to ask the offscreen.

Two options:

- **Cache `browser_id` and `connected` flag in SW state.** Offscreen pushes status updates to SW on WS open/close. SW reports the cached state to popup. Simple, no new round trip.
- **SW forwards GET_STATUS to offscreen via the Port.** Adds a round trip per popup open.

Pick the cache approach — popup is opened by humans, latency matters, and the cache is trivially fresh because offscreen pushes on every state change.

### Server-side changes

**None required.** The server speaks WebSocket to whichever extension component holds the connection; it doesn't care that the extension's internal architecture changed. The PING/PONG protocol is unchanged.

One small CHANGELOG note: `browser_id` is now stable across SW deaths (the WS no longer closes when the SW dies). Tools that observed the previous "reconnected as new br-XXXX" behavior may see fewer such events.

### What goes away

- `keepaliveInterval` (`setInterval` for PING every 20s in SW). Moved to offscreen at 60s cadence as a half-dead detector.
- `socket.onclose → setTimeout(connect, 5000)` in SW. Moved to offscreen with 1s delay.
- `RECONNECT_ALARM` survives but with new semantics ("ensure offscreen exists" instead of "reconnect WS").

### What stays the same

- Server protocol (HELLO, PING/PONG, RESPONSE shape, all command types).
- CLI surface — unchanged.
- All command handler logic in `background.js`.
- `attachedTabs` Set + debugger lifecycle.
- Tests — Python pytest suite is server-side and unaffected.

## Testing

### Existing suite

All 114 existing pytest tests should pass unchanged. They exercise the server only and don't depend on extension behavior.

### Manual smoke (documented in CHANGELOG release notes)

The 0.4.5 release described a smoke that didn't actually work. The 0.6.0 smoke that *should* work:

1. Load the extension fresh.
2. `saidkick tabs` → confirm at least one tab returned with `br-XXXX:N` ID.
3. Wait 5 minutes with no activity.
4. `saidkick tabs` again → confirm same `br-XXXX` (no reconnect-as-new), tabs returned immediately.
5. Manually kill the saidkick server (`pkill -f saidkick`), restart it (`saidkick start`).
6. Within ~5 seconds, `saidkick tabs` → confirm a new `br-XXXX` (the WS had to reconnect across the server restart) but commands work.

### Future: real-Chrome integration test

Out of scope for 0.6.0. A real test would launch Chrome with the extension loaded (via Playwright's `chromium.launchPersistentContext` with `args: ["--load-extension=..."]`), wait 5 minutes idle, then verify the connection is still alive. Worth tracking as a hardening backlog item.

### Verification checklist for the implementer

- [ ] Extension loads without console errors.
- [ ] First `saidkick tabs` after load returns data within 1s.
- [ ] After 5 min idle, `saidkick tabs` still returns data within 1s (no 30s cold-start window).
- [ ] `chrome://extensions` "service worker" link shows the SW going inactive after idle, while `saidkick tabs` continues to work.
- [ ] Killing and restarting the saidkick server produces clean reconnect behavior (new `br-XXXX` minted within 5s).
- [ ] All 114 existing pytest tests pass.

## Out of scope

- Headless-Chrome integration tests for the extension.
- Multi-offscreen-document support (Chrome allows only one per extension anyway).
- Refactoring the SW's `attachedTabs` Set / debugger machinery — those still live in SW and reset on SW death; harmless because re-attach happens on first command that needs CDP.
- Removing PING/PONG entirely — keep at slower cadence as a half-dead-connection detector that the offscreen uses to force a WS reset when the server has silently dropped the socket.
- Changing the popup UI beyond the one-line tweak in `popup.js`.
- The Workspace-level "use saidkick for frontend dev" skill — that's a separate sub-project (own spec, own plan).
